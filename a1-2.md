## Prompt

```text
Act as a professional software tester and suggest test ideas for the feature delimited by three hashes. All test ideas should be focused on discovering risks that impact the quality characteristics: Functionality, Data Integrity and Security
###
* As a paralegal, in order to store and share legal documents, I want to be able to securely upload documents.
* Acceptance criteria:
  - Upload should support the following common file formats: PDF, DOCX, TXT
  - The maximum file size should be 20MB
  - When a document is uploaded it should give a progress update to the user
  - Once uploaded, the document must initially be only accessible to the person who has uploaded it
  - A report of the upload and whether it was successful or not will be stored in the auditing feature
###
```

## Response

## Functionality & Workflow Risks

### File Format & Validation

* **MIME-Type vs. Extension Mismatch:** Upload an executable, script, or image disguised with an allowed extension (e.g., `malware.exe` renamed to `contract.docx` or `script.sh` renamed to `notes.txt`). Verify the server enforces content inspection (magic byte verification) rather than relying solely on the file extension or client-side `Content-Type` header.
* **Format Variations & Edge Formats:**
* Test legacy binary formats (e.g., `.doc`) disguised as `.docx`.
* Upload 0-byte (empty) files with valid extensions (`.pdf`, `.docx`, `.txt`).
* Upload macro-enabled Word documents renamed to `.docx` to check whether execution or ingestion is rejected.
* Test compound extensions (e.g., `affidavit.pdf.exe`, `pleading.docx.txt`).



### File Size Boundaries (20MB Threshold)

* **Binary vs. Decimal Boundary Testing:**
* Exact threshold: Test at 20,000,000 bytes (decimal 20MB) vs. 20,971,520 bytes (binary 20MiB).
* Boundary limits: Upload files at $(20\text{MB} - 1\text{ byte})$, exactly $20\text{MB}$, and $(20\text{MB} + 1\text{ byte})$.
* Extreme payloads: Attempt uploading a significantly oversized file (e.g., 500MB–1GB) to ensure the server terminates the connection early rather than buffering the entire payload into memory.



### Progress Reporting & Network Resiliency

* **Accuracy and State Transitions:** Validate that the progress bar tracks actual chunk-level upload progression rather than an unverified CSS animation. Confirm proper transitions: `Queued` $\rightarrow$ `Uploading (0–100%)` $\rightarrow$ `Processing/Scanning` $\rightarrow$ `Complete`.
* **Disruption and Recovery:** Intercept network traffic, throttle bandwidth to 2G speeds, drop the connection at 50%, and observe behavior. Verify that UI indicates failure, aborts cleanly, and does not show false completion.
* **Concurrent & Multi-Tab Uploads:** Trigger simultaneous uploads of three 20MB documents across multiple browser tabs to confirm session stability, accurate per-file progress tracking, and no race conditions in resource allocation.

### Auditing & Logging

* **State Logging:** Verify that an audit record is created for all possible outcomes:
* Fully successful upload.
* Validation failure (invalid format, oversized file).
* Client-side abort / browser close mid-upload.
* Server-side timeout or storage write failure.


* **Audit Metadata Verification:** Ensure the audit log captures mandatory non-repudiation details: Timestamp (UTC), User ID, Original Filename, File Size, SHA-256 Checksum, Client IP Address, User Agent, and Result Status with clear failure codes.

## Data Integrity & Consistency Risks

### Bit-Level Fidelity & Checksums

* **Cryptographic Verification:** Compute SHA-256 hashes of PDF, DOCX, and TXT files prior to upload. Download the stored file and verify that the hash matches identically, ensuring compression, optimization, or storage pipelines have not altered original legal records.
* **DOCX Structure Preservation:** Upload documents containing complex elements (embedded OLE objects, tracked changes, legal footnotes, digital signatures, embedded fonts) and verify they remain intact upon retrieval without document corruption.

### Character Encoding & Legal Typography

* **TXT Encodings:** Test `.txt` documents saved in UTF-8, UTF-16 (Big/Little Endian), ASCII, and Windows-1252. Verify that legal symbols (`§`, `¶`, `©`, `®`), em-dashes, and accented characters do not render as replacement characters (``) or garbled text.
* **Filename Integrity:** Upload files with names containing Unicode characters, non-English scripts, path separators (`/`, `\`), spaces, and extended symbols (e.g., `Smith vs. State § 102.pdf`). Verify that file storage systems do not truncate, escape-fail, or overwrite files with normalized names.

### Atomic Operations & Orphaned Data Handling

* **Database vs. Object Store Decoupling:** Simulate a database write failure immediately after the file is successfully saved to the storage backend (e.g., S3/Blob storage). Verify:
* The file is not left orphaned without a database pointer.
* The transaction rolls back cleanly.
* The audit log reflects the internal failure accurately.

## Security & Access Control Risks

### Access Control & Authorization (Privileged Isolation)

* **IDOR (Insecure Direct Object Reference):** Capture the document ID or direct file URI generated upon upload. Attempt to access this resource directly using:
* An unauthenticated session (anonymous request).
* A different paralegal's credentials within the same organization.
* A user from a completely different tenant in a multi-tenant setup.


* **Direct Object Storage URL Leakage:** Verify that storage bucket URLs (e.g., pre-signed AWS S3 or Azure Blob URLs) are not publicly readable, are time-bound, and enforce uploader token validation before granting read permissions.

### Malicious Payloads & File Exploits

* **XML External Entity (XXE) Injection:** Since `.docx` files are zipped XML structures, craft a malicious `.docx` archive containing external entity declarations referencing system files (e.g., `<!ENTITY xxe SYSTEM "file:///etc/passwd">`) to test XML parser configurations.
* **Decompression Bombs (Zip Bombs):** Upload a nested or highly compressed `.docx` file (e.g., a 10MB zip that expands to 100GB in memory) to check for server memory exhaustion during document parsing or indexing.
* **PDF-Based Script Execution:** Upload PDFs containing embedded JavaScript actions (e.g., `OpenAction` scripts) or external URI triggers to confirm whether the platform strips, sandboxes, or neutralizes active content prior to storage and previewing.
* **Antivirus & Malware Ingestion:** Test the upload pipeline against standard test strings (e.g., EICAR test file) to ensure malware is quarantined prior to persistent storage and recorded in the audit log.

### Input Sanitization & Audit Log Tampering

* **Stored XSS via File Metadata:** Name a file `<script>alert('xss')</script>.pdf` or `"><img src=x onerror=alert(1)>.docx`. Check if the filename executes in:
* The upload progress modal.
* The document inventory screen.
* The auditing dashboard.


* **Log Injection (CRLF Attacks):** Inject newline characters (`%0d%0a`) into the file name (e.g., `test.txt%0d%0a[AUDIT] Upload success by Admin`) to ensure malicious actors cannot forge entries in flat-file or parsed audit logs.
* **Audit Log Immutability:** Verify that neither the paralegal who uploaded the document nor users with standard edit permissions can alter, mask, or delete records in the auditing feature.
